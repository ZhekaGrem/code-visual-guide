# code-anatomy — L4, компонентне розбиття, accidental complexity

Дата: 2026-09-16. Статус: затверджено в брейнштормі, до реалізації.
Доповнює `2026-09-10-code-anatomy-design.md`, не замінює його.

## 1. Проблема і мета

Скіл показує **статику**: граф імпортів (L1), структуру файлу (L2), порядок читання
фрагмента мовою (L3). Три дірки:

1. **Не видно рантайму.** Як складається система з частин, хто кого викликає в часі, що
   йде паралельно, куди маршрутизується запит, де один ресурс тягне багато потоків, які
   кроки безпечно повторити. Учень бачить файли, але не бачить, **як воно працює**.
2. **Великий репо не влазить.** Один `.md` на репо означає, що гайд і збирається в одному
   контексті, і читається як портянка. На emark (2665 файлів) L2 покриває 12 файлів із 2665.
3. **Не видно, де складність зайва.** Дублювання, два механізми на одну задачу, порушені
   шари — те, що коштує при кожній зміні, але з L1–L3 не читається.

Мета: **L4 «Система»** — рантайм трьома схемами; **компонентне розбиття** — щоб контекст не
губився ні в мене при складанні, ні в учня при читанні; **сторінка accidental complexity** —
на вимогу, з доказом на кожен пункт.

## 2. Ухвалені рішення

| # | Рішення | Чому |
|---|---|---|
| D1 | L4 — **новий рівень у цьому ж скілі**, не окремий скіл | та сама аудиторія й той самий вхід: «поясни цей проєкт» |
| D2 | Шість вимірів → **три схеми**: композиція, маршрутизація, потік у часі | паралельність, multiplexing та ідемпотентність не мають власної форми — це властивості кроків і каналів |
| D3 | **Немає доказу в коді → елемент не пишеться** | інакше гайд починає вигадувати гарантії, яких у системі немає |
| D4 | Компонент = **каскад домен → тека → бандл** | детермінізм: два прогони дають однакове розбиття |
| D5 | Accidental complexity — **окрема сторінка, лише на запит** | це не частина «поясни проєкт» і не code-review |
| D6 | **Другий шаблон** `system_template.html` поруч із `guide_template.html` | L4 має інші форми й інший валідатор; змішувати в одному шаблоні — плутати два рендери |
| D7 | Розкладка **сторінка = файл, компонент = суфікс** | продовжує наявну плоску розкладку `code/emark/`, не ламає імена для малих репо |
| D8 | Маркери рантайму — **в одному `level4.md` за виміром**, а не в шести `lang_*.md` | шість файлів довелось би тримати синхронними |

## 3. Розкладка файлів і компоненти

### 3.1 Імена

```
<сховище>/code/<repo>/
  index_<sha8>.md                    лише при розбитті: L1 на весь репо + таблиця компонентів
  code_guide_<sha8>.md               малий репо: усе одним файлом (поточна поведінка)
  code_guide_<sha8>_<comp>.md        великий репо: L2 + L3 компонента + його зріз L1
  system_<sha8>[_<comp>].md          L4
  complexity_<sha8>.md               лише на запит, завжди на весь репо
  artifacts/<та сама назва>.html
```

`<comp>` — slug `[a-z0-9-]{1,24}`, унікальний у межах репо. Малий репо не отримує ні індексу,
ні суфіксів: раніше згенеровані гайди лишаються валідними.

### 3.2 Поріг розбиття

Рахується після кроку 1 (L1 побудовано). Розбиття вмикається, якщо виконано хоч одне:

- файлів у L1 **> 40**;
- мов **> 1**;
- каскад дав **≥ 3 компоненти по ≥ 8 файлів**.

Інакше — один файл, як зараз.

### 3.3 Каскад «що таке компонент»

1. **Домен.** Сегмент шляху, що повторюється в ≥ 2 шарах (`orders/` і в `controllers/`, і в
   `services/`), або бізнес-тека верхнього рівня. Технічні імена доменами **не** є:
   `controllers`, `services`, `utils`, `models`, `lib`, `common`, `core`, `config`, `test`,
   `tests`, `scripts`, `docs`, `deploy`.
2. **Тека верхнього рівня** — якщо доменів не видно.
3. **Бандл за графом імпортів** — якщо тека одна або теки плоскі: компоненти зв'язності
   неорієнтованого графа імпортів; один гігантський компонент ріжеться за entry point'ами
   (entry + транзитивне замикання; файл, доступний із кількох, іде до найближчого за довжиною
   шляху, за рівності — до першого за алфавітом).

Пост-обробка: компоненти < 5 файлів зливаються в `shared`. Стеля — **8** компонентів; понад —
8 найбільших, решта в `rest`, і рядок про це в індексі. Порядок — за спаданням кількості
файлів, далі алфавіт.

Перед генерацією — один рядок учню: «Розбив на N компонентів: orders (12), catalog (9)…
назви інакше — перероблю». **Не блокує.**

### 3.4 Цикл генерації

```
1. L1 + каскад       → index_<sha8>.md пишеться ОДРАЗУ (L1 JSON + таблиця компонентів, статус pending)
2. для кожного компонента по черзі:
     читаю тільки його файли → code_guide_<sha8>_<comp>.md → HTML → статус done в індексі
3. L4  — окремий прохід, читає індекс і маркери з references/level4.md
4. complexity — окремий прохід, лише на запит
```

Індекс — машинний HANDOFF: обірвалась сесія — видно, на якому компоненті стало.

### 3.5 Що це змінює в лімітах

`L2 ≤ 12 файлів` стає лімітом **на компонент**, не на репо. `l2_note` — свій у кожному
компоненті. Сторінка індексу додає граф компонентів (вузол = компонент, ребро = імпорт між
компонентами).

## 4. L4 «Система»

### 4.1 Наскрізне правило доказу

Кожен вузол, канал, маршрут, крок і бейдж має `evidence: "<шлях>:<рядок>"` або
`"<шлях>:<рядок>-<рядок>"`. Нема на що показати — елемент не потрапляє в дані. Не «unknown»,
не сіра плашка. Єдиний виняток — `kind: "client"`: він виводиться з наявності маршруту.

### 4.2 Схема даних `system_<sha8>[_comp].md`

Рівно один блок json:

```json
{
  "mode": "system",
  "project": "emark", "generated": "YYYY-MM-DD", "git_commit": "string | null",
  "root_path": "string", "source_md": "string",
  "component": "orders | null",
  "scope_note": "L4 для компонента orders: 12 файлів",

  "composition": {
    "nodes": [
      {"id": "api", "kind": "service | worker | store | queue | external | client | scheduler",
       "name": "api", "summary": "≤ 1 речення", "evidence": "docker-compose.yml:12"}
    ],
    "channels": [
      {"from": "api", "to": "postgres", "kind": "http | db | queue | event | fs | grpc | ws",
       "label": "≤ 8 слів", "evidence": "db/client.ts:14",
       "multiplex": {"what": "1 пул × 10 з'єднань на N запитів", "evidence": "db/pool.ts:8"}}
    ]
  },

  "routing": {
    "note": "string | null",
    "routes": [
      {"trigger": "POST /api/orders", "kind": "http | queue | event | cron | cli",
       "handler": "OrderController.create", "evidence": "web/OrderController.java:61"}
    ]
  },

  "flows": [
    {"id": "place-order", "title": "Оформлення замовлення", "trigger": "≤ 15 слів",
     "participants": ["client", "api", "db", "payment"],
     "parallel_groups": [
       {"id": "p1", "kind": "promise_all | goroutine | thread_pool | async_task | batch",
        "evidence": "svc/checkout.ts:40"}
     ],
     "steps": [
       {"n": 1, "from": "client", "to": "api", "action": "≤ 15 слів",
        "evidence": "web/OrderController.java:61",
        "parallel_group": "p1 | null",
        "idempotency": {"verdict": "safe | keyed | unsafe", "key": "order_id | null",
                        "evidence": "db/orders.sql:7"}}
     ]}
  ]
}
```

`composition` → граф; `routing` → таблиця, малюється тільки якщо маршрути знайдено;
`flows` → sequence, де `parallel_group` дає `par/and`, а `idempotency` — бейдж на кроці.

### 4.3 Докази для трьох «невидимих» вимірів

**Паралельність** — конструкція, що *запускає* паралельне виконання: `Promise.all/allSettled`,
`worker_threads`; `go func()`, `errgroup`; `CompletableFuture`, `ExecutorService`, `@Async`;
`asyncio.gather`, `ThreadPoolExecutor`, `asyncio.create_task`. Без такої конструкції кроки
малюються послідовно.

**Multiplexing** — місце, де один ресурс обслуговує багато логічних потоків, із числом, якщо
воно є в коді: пул з'єднань і його розмір, батч і його розмір, один сокет на N підписок
(HTTP/2, WS-кімнати), один консюмер на N топіків, event loop як один потік під N задач.

**Ідемпотентність** — три вердикти, кожен з доказом:

| verdict | Ставиться, коли |
|---|---|
| `safe` | read, PUT повним станом, `ON CONFLICT` / UPSERT за унікальним ключем |
| `keyed` | повтор безпечний **завдяки** ключу або guard'у: idempotency-key, unique-індекс, таблиця дедупу, перевірка «вже оброблено». У `key` — що саме |
| `unsafe` | **лише** коли на шляху видно ретрай або at-least-once доставку **і** ефект пише/шле назовні без знайденого ключа чи унікального обмеження |

Немає ретраю в доказах — бейджа немає взагалі: «не бачу захисту» ≠ «захисту немає».

### 4.4 Ліміти L4

≤ 15 вузлів композиції · ≤ 25 рядків маршрутів (більше → групувати за префіксом + рядок
пояснення) · ≤ 6 потоків на сторінку · ≤ 12 кроків у потоці (довше → різати потік).

### 4.5 Коли L4 будується

Автоматично при depth ≥ 2, якщо знайдено **≥ 2 вузли композиції** з доказами. Не знайдено —
L4 мовчки не будується (як L3 у репо без коду). Порожньої сторінки не буває.

## 5. Сторінка accidental complexity

### 5.1 Схема даних `complexity_<sha8>.md`

```json
{
  "mode": "complexity",
  "project": "emark", "generated": "YYYY-MM-DD", "source_md": "string",
  "scanned": {"files": 120, "components": 5},
  "findings": [
    {"category": "duplication | competing | layering | oversized",
     "title": "≤ 10 слів", "component": "orders | null",
     "what": "≤ 30 слів — що саме повторюється або порушено",
     "cost": "≤ 20 слів — що доведеться правити у двох місцях, коли зміниться правило",
     "evidence": [{"path": "a.ts", "lines": "40-58", "note": "≤ 10 слів"},
                  {"path": "b.ts", "lines": "12-29", "note": "≤ 10 слів"}],
     "excerpt": ["≤ 10 рядків коду", "≤ 10 рядків коду"]}
  ],
  "omitted_note": "ще N дрібних знахідок — назви категорію, покажу"
}
```

### 5.2 Пороги

| Категорія | Потрапляє, коли | Мінімум доказів |
|---|---|---|
| `duplication` | та сама логіка / запит / валідація в ≥ 2 файлах, ≥ 6 подібних рядків | 2 місця |
| `competing` | два живі механізми на одну задачу (два HTTP-клієнти, ORM + ручний SQL, два кеші, дві системи конфігів) — обидва мають вхідні ребра | 2 місця |
| `layering` | ребро повз шар (контролер → БД повз сервіс) або цикл із callout'ів L1 | 1 ребро |
| `oversized` | файл > 400 рядків **і** ≥ 3 різні ролі (ролі перелічити); або експорт із нулем споживачів і не entry | 1 місце + перелік ролей |

≤ 12 знахідок, сортування за кількістю зачеплених файлів, решта — в `omitted_note`.

### 5.3 Тон

Факт + чим болить при зміні. Без вердиктів («поганий код», «жах»), без приписів
(«перепиши на X»), без метрик заради метрик. Сторінка відповідає на одне питання: **де
складність від історії, а не від задачі.**

## 6. Рендерер

### 6.1 `references/system_template.html` — один файл, три режими

`mode` у даних вирішує, що малювати:

| mode | Малює |
|---|---|
| `index` | граф компонентів + таблиця сторінок зі статусами |
| `system` | три схеми L4 |
| `complexity` | картки знахідок |

Самодостатній HTML, єдиний зовнішній ресурс — mermaid із cdnjs, як у `guide_template.html`.
Плейсхолдер один — `{{DATA}}`.

### 6.2 Форми й палітра (знає рендерер, не дані)

Вузли: `service` прямокутник · `worker` прямокутник із подвійною рамкою · `store` циліндр ·
`queue` паралелограм · `external` шестикутник пунктиром · `client` стадіон · `scheduler`
паралелограм із таймером.

Канали: синхронні (`http`, `db`, `grpc`, `fs`) — суцільна стрілка; асинхронні (`queue`,
`event`) — пунктир; потокові (`ws`) — товста. `multiplex` — підпис на ребрі.

**Нових кольорів не додається** (стеля 5 із `boundaries`): `safe`/`keyed` беруть зелений
operation, `unsafe` — червону рамку side effect, паралельна доріжка — сірий structure.

Потоки — mermaid `sequenceDiagram`, `parallel_groups` → `par / and / end`, ідемпотентність →
`Note`. Маршрутизація — HTML-таблиця, не схема: 25 маршрутів у mermaid нечитабельні.

### 6.3 Валідатор

Стиль `guide_template.html`: `GuideError` з назвою поля. Правила:

- `mode` з переліку; для кожного режиму — свій набір обов'язкових полів;
- `kind` з переліку (вузол, канал, маршрут, паралельна група);
- ребро вказує на наявний `node.id`; `from`/`to` кроку є серед `participants`;
  `parallel_group` посилається на оголошену групу;
- `evidence` матчить `^[^\s:]+:\d+(-\d+)?$` **скрізь, крім `kind: "client"`**;
- `verdict: "keyed"` без `key` — помилка; `verdict` без `evidence` — помилка;
- ліміти §4.4 і §5.2 — помилка при перевищенні, не мовчазне обрізання;
- довжини: `action` ≤ 15 слів, `what` ≤ 30, `cost` ≤ 20, `title` ≤ 10, `summary` ≤ 1 речення.

## 8. Правки в скілі

`SKILL.md` (зараз 345 рядків) отримує **маршрут, не деталі** — приріст ≈ 100 рядків:

- `description` у frontmatter: тригери «як працює система», «покажи потік», «схема рантайму»,
  «де дублювання», «accidental complexity»;
- таблиця рівнів: рядок L4;
- крок 1: каскад компонентів, поріг, ігнор `+ .ruff_cache`;
- новий крок 5 «L4», новий крок 6 «complexity — на запит», старий крок 5 стає кроком 7;
- крок збереження: індекс, суфікси компонентів;
- `output_schema`: посилання на дві нові схеми (§4.2, §5.1);
- `boundaries`, «Анти-патерни», «Verification» — нові пункти.

Нові довідники:

- `references/level4.md` — маркери рантайму **за виміром** (композиція / маршрутизація /
  паралельність / multiplexing / ідемпотентність), у кожному — підсекції по мовах
  (js_ts, python, go, java, sql, mongo) і правило «що є доказом». Шість `lang_*.md` **не
  чіпаються**.
- `references/complexity.md` — категорії, пороги, формат знахідки, правила тону.

## 9. Секрети

Доказ може показувати на конфіг, але **значення секрету ніколи не цитується** — ні в
`evidence.note`, ні в `excerpt`, ні в `summary`. Теки й файли, які не читаються взагалі:
`99-credentials/`, `prod-creds/`, `.env`, `.env.*` (крім `.env.example`), `*.pem`, `*.key`,
`id_rsa*`. Композиція будується з `docker-compose.yml`, `.env.example`, маніфестів деплою —
не з робочих секретів.

- три однакові за формою проєкти — очікуваний кандидат у `competing`/`duplication` на сторінці
  complexity, **якщо** доказ покаже спільний код, а не просто схожі назви тек.

## 11. Межі (чого не робимо)

- Не запускаємо код репо, щоб «побачити рантайм» — тільки статичні докази (правило A).
- Не рахуємо метрики якості (cyclomatic complexity, coverage) — це не лінтер.
- Не даємо приписів «перепиши» — сторінка complexity описує, а не призначає.
- Не чіпаємо `lang_*.md` і формат `code_guide_*.md` для малих репо — зворотна сумісність.
- Не робимо автоматичний вибір «що показати» понад ліміти §4.4 — перевищення це помилка
  даних, не привід тихо обрізати.
